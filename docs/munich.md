# Munich · 0.24.0

Munich now covers **40.5 km²**, up from 8.90 km² (**4.55×**). The beta includes the old town, Hauptbahnhof, Maxvorstadt, Schwabing, Theresienwiese, Lehel and Haidhausen. Building shade, sun preference, elevation, calmer streets, water, mapped-barrier avoidance and address search use the expanded area in the shared website, PWA and native app. This is **not citywide coverage**. Select **München · Beta** and use the visible boundary.

## Source and processing record

- **Buildings:** sixteen official 2 km LoD2 CityGML tiles in the configured UTM32 source rectangle `[688000,5332000,696000,5340000]`. The source index is published **6 October 2026** and pinned by SHA-256. All tiles match its published size/hash; old and new source bytes cannot be mixed by download resumption. **68,037 accepted parts / 2,902,264 triangles**; **220 footprint records** remain unknown masks, including malformed ground surfaces and rejected triangulation. The source includes the 291.39 m Olympiaturm: Munich has a reviewed **350 m** building-height ceiling, while other cities retain their existing bound. A collapsed ground surface becomes an explicit unknown mask around the source XY envelope, never a solid shade object. See [building and ground report](munich-shade-data.json).
- **Ground:** [Bavaria DGM1](https://geodaten.bayern.de/opengeodata/OpenDataDetail.html?pn=dgm1), sixty-four 1 km GeoTIFF tiles from the official [Munich metalink](https://geodaten.bayern.de/odd/a/dgm/dgm1/meta/metalink/09162000.meta4). Original 1 m cells are averaged in aligned 2×2 blocks; any invalid input keeps the output unknown. Sixteen million valid 2 m cells, no filled gaps; decimetre storage. Raster `TIFFTAG_DATETIME` values are retained as file metadata, **not asserted as flight dates**. Fetch: 11 October 2026. © Bayerische Vermessungsverwaltung, CC BY 4.0; derived/resampled data.
- **Coordinates:** EPSG:25832 / ETRS89 UTM32, metres; roof and ground heights in **DHHN2016**. WGS84 for map display. The 64 km² source rectangle supplies surrounding shadow casters; leaving that domain can still make a sample unknown. Grid convergence is explicitly applied to solar azimuths. Ground heights do not create terrain-cast shadows.
- **Paths, addresses, barriers and street classes:** dated [Geofabrik Oberbayern extract](https://download.geofabrik.de/europe/germany/bayern/oberbayern.html), snapshot **8 October 2026, 20:21:06 UTC**, fetched 11 October, ODbL / © OpenStreetMap contributors. Original node IDs and connectivity remain intact. The graph includes **381.4 km separately mapped sidewalks**, **19.1 km crossings**, **624.8 km other pedestrian paths/streets**, and **397.7 km street centrelines** (graph lengths, not unique street lengths). These figures do not establish a complete pavement network. No parallel sidewalks or crossings are generated by offsetting roads.
- **Traffic zones:** [Mobilitätsreferat München, Tempo-30-Zonen](https://opendata.muenchen.de/dataset/rad_rsp_tempo30zone_poly), DL-DE-BY-2.0; WFS `mor_wfs:rad_rsp_tempo30zone_poly`, EPSG:25832, fetched 11 October 2026. `status=2` means existing/in operation; 295 source polygons intersect the supported area. The catalogue warns that Radlstadtplan geometry is not positionally exact. Consequently a street needs an independent explicit `maxspeed=30` tag before colouring; contradictory/conditional tags, elevated roads and private drives are excluded. Polygon membership alone never changes routing. Null implementation dates stay null. [Source hashes and feature counts](munich-features-data.json).
- **Addresses:** OSM `addr:street`, `addr:housenumber`, optional postcode. Real point records precede duplicate building labels. A closed building footprint may supply a derived interior label point, explicitly **not** an entrance; the router still checks access and its 45 m snapping limit. The [official municipal address CSV](https://opendata.muenchen.de/dataset/adressen_opendata) was inspected: `STRASSE,STRANAM,HSZ,STADTBEZIRK`, **no coordinates**. It is retained as research evidence, not silently geocoded.

Runtime data loading, worker cancellation, tile checksums, offline packs, unknown exposure, faster-route reference and phone interface all use the existing shared implementation. Zurich's data and model rules are unchanged.

## Reproduce

A normal checkout needs only `npm ci` and `npm run dev`; small derived assets are committed. Raw CityGML, GeoTIFF, GeoPackage and OSM files remain ignored. No runtime API key or hosted routing demo is needed.

With the existing geospatial Python environment and original Munich inputs described in [data sources](data-sources.md):

```sh
npm run data:fetch:munich:coverage
.venv-geo/bin/python scripts/extract-munich-osm.py
.venv-geo/bin/python scripts/extract-munich-environment.py
npm run data:prepare:munich
npm run data:packs
npm run data:verify:munich
npm run data:audit:munich:network
node --import tsx scripts/verify-munich.ts --export-rays
.venv-geo/bin/python scripts/audit-munich-shade.py
npm run check
```

`data:prepare:cities` also reattaches the Munich features, so a routine rebuild does not erase addresses or traffic context. Cached sources and official hashes pin preparation. For a deliberate update, review source schema/licence/dates, retain the old evidence and increment versions before replacing derived assets.

## Verification

[53 real calculations](munich-route-validation.json) cover ten point pairs in June and October, 0/1/5/10/15-minute budgets, both light choices, independent and combined preferences, mapped-barrier avoidance, a waypoint, actual addresses, changed time, night and outside coverage. **All 20 paired Sun/Shade comparisons selected different paths.** Five pairs exercise the newly covered districts. The [network source audit](munich-network-audit.json) checks all **84,827 edges / 75,328 nodes** against original OSM identities and access tags; 93.3% of nodes belong to the largest component. Disconnected areas stay disconnected. Every alternative respects its detour allowance and known-data comparison rules. A different path is evidence that the control works, not proof of field accuracy.

The [independent source audit](munich-shade-audit.json) matches **870/870 rays** against original untriangulated CityGML polygons using separate plane fitting, checks native DGM1 blocks and NREL SPA solar elevation. Its frozen fixture runs in the ordinary automated tests without raw downloads. Boundary-sensitive rays remain reported separately. Browser, native and deployment results are recorded in [progress](progress.md) and [platform](platform.md) after release checks.

Actual screenshots: [desktop](screenshots/munich-expanded-desktop.png), [phone](screenshots/munich-expanded-phone-de.png) and [expanded coverage](screenshots/munich-expanded-coverage.png). Browser, installed-PWA and Android-emulator checks are recorded in [platform evidence](platform.md). The live site is [coolerwalks.ch](https://coolerwalks.ch/de/?view=planner), with its existing password gate. Locally: `npm ci`, then `npm run dev`; production preview: `npm run build`, then `npm run preview`.

## Open: parity that is not yet supported

The [new source review](munich-source-review.md) contains reproducible laser/infrared and vehicle-counter samples, not only catalogue links.

1. **Tree shade.** The 2024 tree product supplies positions and heights, not crown outlines/vertical foliage geometry. Bavaria's [published laser classification](https://www.ldbv.bayern.de/mam/ldbv/dateien/laserdaten_punktklassenbeschreibung.pdf) puts vegetation together with other objects in class 20; treating every object return as a tree would be wrong. Open [laser](https://geodaten.bayern.de/opengeodata/OpenDataDetail.html?pn=laserdaten) and [DOM20](https://geodaten.bayern.de/opengeodata/OpenDataDetail.html?pn=dom20) sources exist. The inspected 1 km² sample has winter-2022 laser observations and summer-2024 infrared imagery, with unresolved object classification and epoch differences. Next: validate a vegetation-only mask, for example with suitable contemporaneous imagery, distinguish non-vegetation objects, then build and audit canopy columns. Do not invent circular crowns from tree height.
2. **Complete pavement / side-of-street selection.** Existing OSM sidewalks are used, but their coverage and crossings do not replace Zurich's municipal network. The official [shared foot/cycle map](https://opendata.muenchen.de/dataset/rad_rsp_gemradfusswege_line) is cartographic and explicitly not positionally exact. A complete, connected, suitably licensed pedestrian-surface/crossing dataset or an audited expansion of explicit OSM paths is still needed. Never promise which pavement is shaded on centreline sections.
3. **Street-level vehicle counts.** Munich publishes a [2022 traffic-volume map](https://stadt.muenchen.de/infos/verkehrsdaten.html), largely extrapolated typical-workday totals, and uses [DAVe](https://opensource.muenchen.de/de/software/dave.html) for counts. Bavaria’s licensed BAYSIS WFS was queried: all four nearby 2021 counters fall outside the expanded walking area, and its daily averages are not hourly profiles. No suitable municipal hourly export was verified. DAVe's software licence is not a licence to its database. Obtain an export/API with coordinates, directions, observation dates, intervals and reuse terms before importing counts. **Live traffic remains unavailable in Zurich as well.**
4. **Complete official address coordinates.** The public municipal CSV alone cannot locate a house. Current OSM search is useful but incomplete; the official Bavaria coordinate product is paid and its deployment/reuse terms still need review. No purchase was made.
5. **Wider Munich coverage and walking-surface heights.** This release closes the earlier central-area expansion task, with 40.5 km² of walking coverage and a 64 km² model. Full municipal coverage remains a later, separately audited expansion. Bridges, tunnels and other missing walking heights remain unknown.
6. **Field accuracy and comprehensive accessibility.** Shade, traffic context, actual access, barriers and map-side alignment still need local field validation. Seasonal foliage, cloud/weather effects, terrain shadows and complete wheelchair suitability are not solved by these new data imports.
